1. North star

Evaluation is a steering system, not a scorecard added at the end. Its quality is bounded first by whether the tasks represent real user work, then by whether the oracle or judge measures the intended construct. A sophisticated metric over the wrong population answers the wrong question precisely.
PriorityQuestion
1. RepresentativenessDoes the dataset match the tasks, users, and failure distribution that matter?
2. Oracle validityCan correctness be checked from state, evidence, or a contractual invariant?
3. Judge validityHas the scoring instrument been validated against labels or a known condition?
4. Task successDid the user’s job get done, not merely receive polished prose?
5. ConsistencyDoes the system succeed reliably across repeated attempts where every attempt matters?
6. OperationsCan the run be reproduced, diagnosed, shipped, and monitored without changing the claim?

4. Controlled comparison pattern

No same-configuration control, no causal result. Run the baseline configuration twice to estimate its drift, and run the treatment configuration twice when its stability is unknown. Stability is a property of a configuration and measurement layer, not a universal constant of the harness.

4.1 Pre-register before generating

  • The single variable intended to change.
  • The primary metric and every guardrail.
  • A minimum meaningful effect and equivalence bounds.
  • The sample size and what effect it can realistically distinguish.
  • Decision branches: ship, reject, equivalent, or inconclusive.

4.2 Compare the same cases

Pair on a stable semantic key. Identifiers created independently by two pipelines may look compatible while pointing to different inputs. Print a few pairs for human verification before publishing a result.

4.3 Keep measurement layers separate

LayerExample boundaryUse
ServiceModel request to model responseCompare model-service behavior.
ClientService plus transport and client overheadMeasure the calling system.
Agent turnAssembly, tools, model calls, and orchestrationApproximate user waiting time.
TrialAgent turn plus gradersMeasure harness execution, not product latency.
Wall clockAll scheduling and serializationOperational planning only.

Every layer needs its own control. Repeating an uncontrolled comparison at another layer is not independent corroboration.

5. Conversation-assistant pattern

Aggregate quality scores are not sufficient when a small number of failures are unacceptable. Combine:

InstrumentPurpose
Task-success assertionDid the assistant answer or complete the requested job?
Speaker/addressee checkDid it attribute statements and requests to the correct participant?
Retrieval-honesty checkDid it distinguish “not found” from “does not exist”?
Critical-failure ruleDid any response create a safety, factual, or trust-breaking failure?
Quality rubricWas the useful answer clear, relevant, and readable?
Category reportWhich scenario class produces the failures?
Why categories matter A single pass rate tells you whether the suite moved. A scenario-level breakdown tells you what to fix. Once a category is saturated, move evaluation budget toward weak or underrepresented categories instead of adding more easy cases.

6. Cross-context agent pattern

For an agent that searches multiple sources and can take action, response quality is only one scorecard. Track the sets and transitions separately:

authorized → selected → retrieved → cited → used in answer → delivered outcome
ContractQuestion
Identity and authorizationWhich principal is running, and what is it allowed to read or change?
DiscoveryDid the system consider the relevant sources?
RetrievalDid the necessary evidence enter the agent’s context?
CitationWhich evidence became visible in the response?
Answer coverageWere the key points supported and included?
ExecutionWere the right tool and parameters used?
Final stateDid the intended state change actually occur?
AudienceWas the result delivered to the correct people or destination?

Citation recall is a lower bound on retrieval recall whenever the grader sees only response-visible citations. Instrument the full retrieved set before using citation metrics as a retrieval gate.

7. Validate the judge

7.1 Check discriminative power

Split cases by a condition already known to matter—for example, whether required evidence was available. A useful judge should move in the expected direction. A flat judge may still serve as a regression alarm, but it should not decide improvement.

7.2 Count headroom in cases

A judge near its ceiling cannot show improvement. Report the number of cases that could still improve, not only a mean and standard deviation.

7.3 Validate the construct

A judge can follow its rubric perfectly and still reward the wrong product behavior. Ask what score it gives to a correct decision to do almost nothing, abstain, or ask for clarification.

7.4 Treat explanations as unverified

Judge rationales are diagnostic text, not evidence. Verify any factual statement before quoting it in a decision document.

8. Run integrity and silent failure

A number that a failure can also produce is not a check. If failed trials retain their identifiers, counting identifiers can report a complete run with missing outputs. Verify the property you care about directly.
CheckWhy it is stronger
Exact successful output IDsDistinguishes submitted work from completed work.

9. Shipping evidence chain

A strong change description records:

  • The exact treatment variable and effective configuration.
  • Dataset provenance, version, population, exclusions, and overlap.
  • Controls, primary metric, equivalence bounds, sample limits, and headroom.
  • Run-integrity evidence and complete error/coverage denominators.
  • The supported claim, rejected claims, and unresolved uncertainty.
  • Enablement plan, rollback, monitoring signal, and owner.

10. Failure library

Failure patternPreventive rule
A treatment looks faster than the baselineCompare the effect with same-configuration drift at the same measurement layer.
A small sample creates a compelling mechanism storyState power limits before the run and do not generalize from one shard.
Cross-report pairing yields dramatic resultsPair on normalized content and manually inspect representative pairs.
A run contains all expected IDs but less workRequire successful outputs and independent side-effect checks.
Every judge passesCheck saturation, headroom, and whether scores move on a known condition.
A high average hides trust-breaking failuresAdd critical-failure and zero-tolerance rules.
A response-visible metric is treated as full-system truthDocument the grader’s observation boundary and instrument hidden state.
A run scores well under the wrong identity or routeRead back runtime identity and effective configuration independently of scores.
An observational trend reverses after stratificationSearch for case-mix confounders before interpreting aggregate curves.
A metric exists but never blocks a changeVerify registry, execution, blocking policy, and required merge checks separately.

11. Minimum Definition of Done

  1. The user contract and maximum evidence claim fit in one sentence each.
  2. A machine-readable manifest records the actual system configuration and environment.
  3. The dataset has provenance, versioning, representative task classes, and hard negatives.
  4. Deterministic or state-based oracles are used wherever possible.
  5. Every model-based judge has demonstrated validity, headroom, and defined error handling.
  6. Comparisons use paired cases, same-configuration controls, and pre-registered decision bounds.
  7. The report preserves errors, missing outputs, not-applicable cases, and grader coverage.
  8. The decision package distinguishes landing, enablement, enforcement, and user impact.
  9. Production feedback refreshes the task distribution and regression suite.
